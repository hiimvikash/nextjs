# 19. Next.js Error Handling with error.tsx 

## Introduction to Error Handling
Error handling is a crucial aspect of web applications, implemented in Next.js through a special file called `error.tsx`.

## Current Application State
- Working URL: `localhost:3000/products/1/reviews/1`
- Shows the first review of the first product
- Corresponds to `page.tsx` file in the review ID folder

// Outside component - utility function
function getRandomInt(count) {
  return Math.floor(Math.random() * count);

// Inside component
const random = getRandomInt(2); // Returns 0 or 1

### Error Behavior in Different Modes

**Development Mode:**
- Shows unhandled runtime error with custom message
- Error message: "Error loading review"

**Production Mode:**
- Build: `npm run build`
- Start: `npm run start`
- Shows generic "Application error - A server side exception has occurred"
- Actual error appears in terminal only

### Problems with Unhandled Errors
- Generic error messages aren't helpful to users
- Error in deeply nested components breaks the **entire application**
- Poor user experience

## Solution: error.tsx File

### Implementation Steps
1. Create `error.tsx` file adjacent to `page.tsx` in the review ID folder
2. Must be a **client component** (requires `"use client"` directive)
3. Export default function that returns JSX

```javascript
"use client";

export default function ErrorBoundary() {
  return (
    <div>
      Error in review ID
    </div>
  );
}
```

### Key Requirements
- **Must be client components** - Add `"use client"` at the top
- Acts as error boundary around the `page.tsx` file
- Requires server restart after creation

## Error Boundary Benefits

### Graceful Error Handling
- Only the affected component is replaced
- Rest of the application continues working:
  - Header remains functional
  - Featured products from layout still display
  - Footer stays intact
- **Containment**: Errors are isolated to specific segments

### Using Error Props
Error component receives error object as prop:

```javascript
"use client";

export default function ErrorBoundary({ error }) {
  return (
    <div>
      {error.message}
    </div>
  );
}
```

This displays the actual error message: "Error loading review"

## Power of error.tsx in App Router

### Automatic Error Boundaries
- Automatically wraps route segments and nested children in React error boundary
- Uses file system hierarchy for custom error UIs
- Isolates errors to affected segments only

## Component Hierarchy Overview

The complete component hierarchy in Next.js App Router:

1. **Layout Component** (top level)
2. **Template Component**
3. **Error Boundary** (from error.tsx) - for runtime errors
4. **Suspense Boundary** (from loading.tsx)
5. **Error Boundary** (from not-found.tsx) - for missing resources
6. **Page Component** (bottom level)

## Best Practices
- Always style error components to match your application design
- Use error.message for more informative error displays
- Remember that error boundaries must be client components
- Consider error boundaries at different levels of your application hierarchy

## Simple Explanation
Think of error.tsx as a "safety net":
- **Without error.tsx**: One broken component crashes the entire app (like a house of cards)
- **With error.tsx**: Broken components are contained while the rest continues working (like having fire doors in a building)

# 20. Next.js Error Recovery with Reset Function

## Error Recovery Overview
While some errors are serious, others might be temporary and can be fixed with a simple retry mechanism. Next.js provides error recovery through the reset function in error boundaries.

## Understanding Error Types
- **Serious errors**: Require immediate attention and fixes
- **Temporary errors**: Can often be resolved with a simple retry (network timeouts, temporary server issues)

## Basic Reset Function Implementation

### Error Boundary Props
The error boundary in `error.tsx` provides two useful props:
1. **error**: The error object containing error details
2. **reset**: A function that returns void for retrying component rendering

### Basic Implementation
```javascript
"use client";

export default function ErrorBoundary({ error, reset }) {
  return (
    <div>
      <p>{error.message}</p>
      <button onClick={reset}>
        Try again
      </button>
    </div>
  );
}
```

### Basic Reset Limitations
- **Client-side only**: Simple reset only attempts client-side re-rendering
- **Same error pattern**: If the underlying issue persists, the error will keep occurring
- **Limited effectiveness**: Doesn't refresh server-side data or state

## Advanced Server-Side Recovery

### Required Imports
```javascript
import { useRouter } from 'next/navigation';
import { startTransition } from 'react';
```

### Implementation Steps

1. **Setup router hook:**
```javascript
const router = useRouter();
```

2. **Create reload function:**
```javascript
const reload = () => {
  startTransition(() => {
    router.refresh();
    reset();
  });
};
```

```
Use startTransition() when:

You're doing a state update that is non-urgent.

That update might cause slow rendering.

You still want the app to stay responsive during that update.
```

3. **Update JSX:**
```javascript
<button onClick={reload}>
  Try again
</button>
```

### Complete Advanced Implementation
```javascript
"use client";

import { useRouter } from 'next/navigation';
import { startTransition } from 'react';

export default function ErrorBoundary({ error, reset }) {
  const router = useRouter();
  
  const reload = () => {
    startTransition(() => {
      router.refresh();
      reset();
    });
  };

  return (
    <div>
      <p>{error.message}</p>
      <button onClick={reload}>
        Try again
      </button>
    </div>
  );
}
```

## How Advanced Recovery Works

### startTransition Purpose
- **Deferred execution**: Ensures refresh is deferred until the next render phase
- **State management**: Allows React to handle pending state updates before proceeding
- **Non-blocking**: Prevents UI from freezing during the recovery process

### router.refresh() Function
- **Server-side refresh**: Refreshes the current route from the server
- **Data refetch**: Fetches fresh data from server components
- **Cache invalidation**: Clears any cached data that might be causing issues

### Recovery Process
1. User clicks "Try again" button
2. `startTransition` wraps the recovery process
3. `router.refresh()` fetches fresh data from server
4. `reset()` attempts to re-render the component
5. If successful, user sees the actual page content


## Simple Explanation
Think of error recovery like:
- **Basic reset**: Like pressing "refresh" on a webpage that failed to load
- **Advanced recovery**: Like clearing your browser cache AND refreshing - getting completely fresh data from the server

The advanced approach gives you a better chance of recovery because it addresses both client-side and server-side issues.

# 21. Error Handling in Nested Routes

## Key Concept: Error Bubbling

**Error Bubbling Rule**: Errors always bubble up to find the closest parent error boundary.

- An `error.tsx` file handles errors for its own folder AND all nested child segments below it
- Strategic placement of `error.tsx` files controls the level of detail in error handling

## Route Structure Example

```
products/
├── [product-id]/
│   └── review/
│       └── [review-id]/
│           └── error.tsx
```

## Error File Placement Impact

### Case 1: Error.tsx in Product Route (Higher Level)
- **Location**: `products/error.tsx`
- **Effect**: When error occurs in review section, the ENTIRE products route gets replaced
- **Result**: Less precise error handling - affects more of the UI

### Case 2: Error.tsx in Review ID Route (Lower Level)
- **Location**: `products/[product-id]/review/[review-id]/error.tsx`
- **Effect**: Only the review component gets replaced when error occurs
- **Result**: More precise error handling - featured product section remains intact

## Simple Explanation

Think of error boundaries like safety nets at different floors of a building:
- Higher placement = catches errors from more floors below but affects larger area
- Lower placement = catches errors from fewer floors but affects smaller, specific area

## Key Takeaway

**Where you place your `error.tsx` file determines exactly which parts of your UI get affected when errors occur.**

- For broad error handling → Place `error.tsx` higher in route hierarchy
- For precise error handling → Place `error.tsx` closer to the component that might error

# 22. Error Handling in Layouts

## The Layout Error Problem

**Key Issue**: `error.tsx` cannot catch errors thrown in `layout.tsx` within the same segment.

### Why This Happens

<img width="847" alt="image" src="https://github.com/user-attachments/assets/5633c300-5805-403f-ad0d-19c4a9669064" />

**Component Hierarchy**: The layout sits **above** the error boundary in the component tree.


## Practical Example

### Setup
- Route structure: `products/[product-id]/`
- `error.tsx` placed in `[product-id]` folder
- Error thrown in `layout.tsx` of the same `[product-id]` segment

### What Happens
- Error occurs in `products/[product-id]/layout.tsx`
- `products/[product-id]/error.tsx` **cannot** catch it
- Result: Unhandled runtime error - app breaks completely

## The Solution

**Move the error boundary up one level** to the parent segment.

### Before (Doesn't Work)
```
products/
└── [product-id]/
    ├── layout.tsx (throws error)
    └── error.tsx (can't catch layout error in same segment)
```

### After (Works)
```
products/
├── error.tsx (can catch layout errors from child segments)
└── [product-id]/
    └── layout.tsx (throws error)
```

## Simple Explanation

Think of it like a safety net analogy:
- You can't catch yourself falling - you need someone else to catch you
- A layout can't be caught by an error boundary in the same "room"
- The error boundary needs to be in the "room above" to catch layout errors

## Key Rule

**For layout errors**: Always place `error.tsx` in the **parent segment** of the layout that might throw errors.

## Result After Fix
- Error boundary renders properly
- Only the products route content gets replaced
- Higher-level UI elements (header, footer) remain intact

## Important Takeaway

Error boundaries work differently for layouts vs pages:
- **Pages**: Error boundary in same segment works
- **Layouts**: Error boundary must be in parent segment

# 23. Global Error Handling in Root Layout

## The Root Layout Problem

**Question**: If error boundaries can't catch errors in layouts from the same segment, what about errors in the root layout? It has no parent segment.

**Answer**: Next.js provides a special `global-error.tsx` file for this scenario.

## Global Error.tsx

### Purpose
- **Last line of defense** when something goes catastrophically wrong at the highest level
- Handles errors in root layout and nested routes when no other error boundary exists
- Goes in your **root app directory**

### Setup Example

#### 1. Create Error Wrapper Component
File: `app/error-wrapper.tsx`

```jsx
'use client' // Must be client component

// Error simulator that throws error when button clicked
// Accepts message prop and throws error when error flag is true
// Wrapped around children in root layout
```

#### 2. Update Root Layout
File: `app/layout.tsx`

```jsx
import ErrorWrapper from './error-wrapper'

// Wrap children with ErrorWrapper component
<ErrorWrapper>
  {children}
</ErrorWrapper>
```

#### 3. Create Global Error File
File: `app/global-error.tsx`

```jsx
'use client' // Must be client component

export default function GlobalError() {
  return (
    <html>
      <body>
        <h2>Something went wrong</h2>
        <button onClick={() => window.location.reload()}>
          Refresh
        </button>
      </body>
    </html>
  )
}
```

## Key Requirements for Global Error

### 1. Must Include HTML and Body Tags
- When global error kicks in, it **completely replaces your root layout**
- Since root layout contains `<html>` and `<body>`, global error must include them too

### 2. Only Works in Production Mode
- **Development**: Shows default Next.js error overlay instead
- **Production**: Shows your custom global error UI

#### Testing Steps:
```bash
# Stop development server
Ctrl + C

# Build for production
npm run build

# Start production server
npm run start
```

## Simple Explanation

Think of global error as the **emergency backup system**:
- Regular error boundaries = fire extinguishers on each floor
- Global error = building's main fire suppression system
- Only activates when all other systems fail

## Best Practices

### Keep Global Error Simple
- **Recommended**: Use only HTML and CSS
- **Avoid**: Complex JavaScript or external dependencies
- **Reason**: You can't catch errors from the global error boundary itself

### Why Simple is Better
- No risk of the error handler itself throwing errors
- Ensures the fallback UI always works
- Provides reliable user experience even in worst-case scenarios

## Key Differences from Regular Error.tsx

| Feature | Regular Error.tsx | Global Error.tsx |
|---------|------------------|------------------|
| **Scope** | Segment + children | Entire application |
| **Requirements** | Standard component | Must include HTML/body |
| **Environment** | Works in dev + prod | Production only |
| **Complexity** | Can be complex | Should be simple |

## Important Takeaways

1. **Global error is your safety net** for root layout errors
2. **Production-only feature** - won't show in development
3. **Must include HTML and body tags** for proper rendering
4. **Keep it simple** to avoid errors in the error handler itself
